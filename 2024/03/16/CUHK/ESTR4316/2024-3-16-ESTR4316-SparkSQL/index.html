Spark SQL

Created2024-03-16|Updated2024-03-16|ESTR4316
|Post View:

Introduction

Efficient In-Memory Storage

  • Simply caching Hive records as Java objects is inefficient due to high per-object overhead
  • Instead, Shark employs column-oriented storage using arrays of primitive types
    • Row-oriented storage is more suitable for real time searching (such as real-time transaction processing)
    • Column-oriented storage is more suitable for big data systems for anlyzing, like search the frequent objects within the whole dataset that requires to scan the whole column

Approaches

  • Spark SQL introduces a Tightly Integrated way to work with a new abstraction of Structured Data called SchemaRDD (a.k.a. DataFrame), which is a Distributed Collection of Rows (i.e. a Table) with Named Columns

  • It supports the Transformation of RDDs using SQL: In particular, DataFrames (aka SchemaRDDs) is an abstraction which supports Selecting, Filtering, Aggregating and Plotting Structured data

  • Spark SQL v.s. Shark

    • Shark modified the Hive backend to run over Spark but had two challenges:

      1. Limited integration with Spark programs
      2. Hive Optimizer not designed for Spark

    • Spark SQL

      • reuses some parts of Shark: Hive Data Loading and In-memory Column-store
      • adds the features: RDD-aware Optimizer and Richer Language Interfaces

  • RDDs v.s. SchemaRDDs

    • Spark + RDDs: Functional transformations on Partitioned Collections of Opaque Objects
    • SQL + DataFrames (aka SchemaRDDs): Declarative transformations on Partitioned Collections of Tuples

  • Data Model

    • Nested data model
    • Supports both primitive SQL types (boolean, integer, double, decimal, string, data, timestamp) and complex types (structs, arrays, maps, and unions); also user defined types.
    • First class support for complex data types

Schema

Relational operations

  • Relational operations include select, where, join, groupBy via a DSL
  • Operators take expression objects
  • Operators build up an abstract syntax tree (AST), which is then optimized by Catalyst
  • Alternatively, register as temp SQL table and perform traditional SQL query strings

Caching Tables In-Memory

SparkSQL can cache tables using an in-memory columnar format:

  • Scan only required columns
  • Fewer allocated objects (less Garbage Collection)
  • Automatically selects best compression

JSON Support

  • We can use jsonFile or jsonRDD to convert a collection of JSON objects into a DataFrame
  • Infer and Union the schema of each record
  • Maintain nested structures and arrays

Conclusion

  • SQL is wildly popular and important for real-world customers
  • Schema is very useful
    • In most data pipelines, even the ones that start with unstructured data end up having some implicit structure
    • Key-value abstraction (under RDD) is too limited
    • Nevertheless, Support for Semi/Un-structured data is critical!
  • Separation of Logical vs. Physical Plan is important for Performance Optimizations, e.g. join selection.
