Introductory

Pig is a large-scale data processing system, the scripts are written in Pig Latin, a dataflow language

  • Pig Engine Parses: compiles Pig Latin scripts into MapReduce jobs run on top of Hadoop
  • Pig Latin: a dataflow language
  • Pig: the high level language interface for Hadoop

Why not MapReduce

Compute the natural join $R(A,B) \Join S(B,C)$

  • Implementation in MapReduce:
    1. Each input tuple R(a,b) into key-value pair (b,(a,R))
    2. Each input tuple S(b,c) into (b,(c,S))
    • Map processes send each key-value pair with key b to Reduce process h(b)
    • Each Reduce process matches all the pairs (b,(a,R)) with all (b,(c,S)) and outputs (a,b,c)

The implementation is complicated, we need a faster code development

Although the performance is on par with (maybe ~2 times slower than) raw Hadoop, it is convenient in the development

Pig Components

  • Two Main Components:

    1. High-level language (Pig Latin)
    2. Two execution modes
      • Local: reads/writes to local file system
      • Mapreduce: connects to Hadoop cluster and reads/writes to HDFS

  • Two modes:

    1. Interactive mode: using console
    2. Batch mode: submit a script

  • Pig Compilation

Pig Latin

Language Features

  • Keywords
    Load, Filter, Foreach Generate, Group By, Store, Join, Distinct, Order By, …

  • Aggregations
    Count, Avg, Sum, Max, Min

  • Schema
    Defines at query-time not when files are loaded

  • User Defined Functions (UDFs)

    • As first-class citizens in the language
    • UDFs can be written in other languages, e.g. Java, Python, Javascript, etc

Data Types

  1. Atom: a simple atomic value
    'alice'
  2. Tuple: a sequence of fields, each can be any of the data types
    ('alice', 'lakers')
  3. Bag: a collection of tuples (similar to set)
    {('alice', 'lakers'), ('alice', ('iPod', 'apple'))}
  4. Map: a collection of data items that is associated with a dedicated atom (similar to the dictionary)
    ['fan of' -> {'lackers', 'iPod'}, 'age' -> 20]

Expressions

Expression Type Example Value for tuple t
Constant 'bob' Independent of t
Field by position $0 $\text{‘alice’}$
Field by name f3 $[\text{‘age’} \rightarrow 20]$
Projection f2.$0 $\begin{Bmatrix} (\text{‘lackers’}) \\ (\text{‘iPod’}) \end{Bmatrix}$
Map Loopup f3#'age' $20$
Function Evaluation SUM(f2.$1) $1 + 2 = 3$
Conditional Expression f3#'age' > 18 ? 'adult' : 'minor' $\text{adult’}$
Flattening (remove the bags and tuples) FLATTEN(f2) $\text{‘lackers’}, 1, \text{iPod’}, 2$

Commands and Operations

  1. LOAD: Specify input data

  2. FOREACH: Per-tuple processing

  3. FLATTEN: Remove the nested data in tuples (or bags)

  4. FILTER: Discarding unwanted data

  5. COGROUP: Getting related data together

  6. JOIN: Cross product of two tables

  7. STORE: Create output

  8. Other operators such as UNION, CROSS, ORDER, DISTINCT, LIMIT

Additional Operators

  1. Re-partition Join: using parallel x to customise the number of partitions

  2. Replicated Join: using using 'replicated' to conduct the replicated join
    Optimization in joining a big dataset with a small one

  3. Multiple Outputs: Pig is able to produce multiple outputs to different files

User Defined Function

  • Types of UDF’s:

    • Eval Functions (extends EvalFunc<String>)
    • Aggregate Functions (extends EvalFunc<Long> implements Algebraic)
    • Filter Functions (extends FilterFunc)

Pig Latin vs. SQL

  • Pig Latin

    • Pig Latin is procedural (dataflow programming), step-by-step query style is much cleaner and easier to write
    • Lazy evaluation: data not processed prior to STORE command
    • Data can be stored at any point during the pipeline
    • Schema and data types are lazily defined at run-time
    • An execution plan can be explicitly defined (Use optimizer hints)

  • SQL

    • SQL is declarative but not step-by-step style
    • Query plans are solely decided by the system
    • Data cannot be stored in the middle
    • Schema and data types are defined at the creation time

Optimization

  1. Schema and type checking
  2. Translating into efficient physical dataflow (i.e., sequence of one or more MapReduce jobs)
  3. Exploiting data reduction opportunities (e.g., early partial aggregation via a combiner)
  4. Executing the system-level dataflow (i.e., running the MapReduce jobs) n Tracking progress, errors, etc.
  • Logic Plan: The Pig Latin script
  • Physical Plan: Automatically optimize the executions

Apache Tez

  • Tez is a distributed execution framework targeting data-processing applications
    • NOT a standlone computation engine like MapReduce or Spark ; Instead, it is intended to be use as a “backend” library
  • Based on expressing a computation as a DAG dataflow graph
  • Highly customizable to meet a broad spectrum of use cases
  • Built on top of YARN: the resource management framework for Hadoop

Usage

TeZ is an Alternative Execution Library for realizing Pig’s Logical Computation Plan

  1. The Required Data Processing Flow is represented as a Directed-Acyclic Graph (DAG) (which is what PIG has been doing all along)
  2. TeZ can then be used to realize/execute the DAG-based dataflow/computation to avoid limitations imposed by the rigid 2-stage MapReduce model
